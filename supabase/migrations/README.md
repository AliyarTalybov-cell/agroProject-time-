# Миграции

Правила именования и применения — в корневом `CLAUDE.md`, раздел «Миграции».
Здесь только то, что касается этого каталога и не описано там.

## Порядок применения старых миграций восстановить нельзя

В каталоге 82 файла. 81 из них пришёл в репозиторий **одним коммитом**
`593097a` от 14 августа 2026 года, имена — без дат и номеров (`add_…`,
`fix_…`, `zz_…`). Ни git, ни сортировка по алфавиту настоящего порядка
не дают.

Это не мелочь. Находка 4 аудита выросла ровно отсюда: приватная политика
на `chat_messages` из чат-миграции была перекрыта политикой `using (true)`
из `restrict_delete_to_manager_only.sql` — просто потому, что вторую
применили позже. Разрешающие политики в Postgres складываются через ИЛИ,
и результат зависел от очерёдности, которую никто не фиксировал.

**Переименовывать старые файлы задним числом не нужно.** Мы не знаем их
настоящего порядка, а проставленные даты выглядели бы как знание и
закрепили бы выдумку в именах.

## Источник истины — база, а не каталог

Вместо восстановления истории заведён журнал: таблица
`public.applied_migrations`, миграция `20260820_migration_ledger.sql`.
Выполнив миграцию в SQL Editor, добавляйте о ней запись:

```sql
insert into public.applied_migrations (filename, note)
values ('20260901_что_то.sql', 'коротко, что сделано');
```

Что уже применено:

```sql
select filename, applied_at, applied_by, note
from public.applied_migrations
order by applied_at;
```

Журнал заполняется вручную и полным быть не обязан — старые 81 миграция в
него не внесены, потому что неизвестно, какие из них выполнялись и в каком
виде. Он отвечает на вопрос «что применяли начиная с августа 2026», а не
«из чего сложилась текущая схема».

## Как узнать текущее состояние схемы

По файлам — никак, только запросом к базе. Полезные:

```sql
-- политики: кому и что разрешено
select schemaname, tablename, policyname, roles, cmd, qual
from pg_policies
where schemaname = 'public'
order by tablename, policyname;

-- политики без указания роли действуют и на anon
select tablename, policyname, roles
from pg_policies
where schemaname = 'public' and roles = '{public}'
order by tablename;

-- гранты для анонимной роли: anon-ключ публичен и лежит в бандле
select table_name, privilege_type
from information_schema.role_table_grants
where grantee = 'anon' and table_schema = 'public'
order by table_name;
```

Вторая и третья проверки — прямое следствие находок 3 и 4. Их стоит
прогонять после каждой миграции, которая трогает политики.
